# 写作框架与正反例对照

## 1. 信息采集清单（写之前先凑齐）

| 类别 | 要拿到的事实 |
|---|---|
| 场景与约束 | 服务谁、什么负载（日均请求 / 文档量 / 并发）、原来卡在哪（准确率、延迟、成本、人工占比） |
| 你的层 | Runtime / 编排 / 沙箱 / 工具层 / 上下文记忆 / 可观测性 / 评测，明确是哪一到两层 |
| 关键决策 | 技术选型及取舍（为什么选它、放弃了什么、接受什么代价） |
| 指标 | 至少 2 个可核验数字 + 测量口径（测试集来源、对比基线、时间窗口） |
| 边界 | 生产 / 内部 / 课程 / 原型；有无真实用户与生产数据 |
| 失败与评测 | 失败路径处理、评估集 / 回归 / A/B 是否存在 |

## 2. 项目四段式（项目条目的默认骨架）

1. **场景与约束**：谁在用、什么负载、原来卡在哪（例「单一意图识别准确率不足 70%，多轮上下文丢失」）
2. **你负责的那一层**：Runtime / 编排 / 沙箱 / 工具层 / 可观测性中的哪一个，不写「全链路架构师」
3. **关键决策与取舍**：为什么选它（「选 microVM 而非容器，接受内存开销换硬件级隔离」）
4. **可核验指标**：完成率、p95 延迟、单任务成本、冷启动、GPU 利用率、人工升级率——都能说出怎么测的

压缩成 bullet 时每条 = 动作 + 决策/机制 + 数字；3-5 条讲完，别摊成任务清单。

## 3. Agent 四要素（项目内容主线，对应 infra 岗技术叙事）

| 要素 | 该写什么 | 句式示例 |
|---|---|---|
| 工具定义 | 定义了哪些工具、边界与接口规范、扩展方式 | 「设计并实现知识库检索、行情查询、保费计算、合规审查 4 类工具，统一 JSON 输入输出规范，经 Adapter 层调度，新工具接入不改主循环」 |
| 控制策略 | Tool Router / Orchestrator、调用范式取舍 | 「实现 Tool Router 按上下文选择调用路径，支持 ReAct 与 Plan-Execute 两种范式按任务类型切换，任务完成率提升 X%」 |
| 决策逻辑 | 规则触发 + 模型推理怎么结合、多轮调用链、强约束场景 | 「关键词规则 + LLM 推理双通道决策，高风险场景（金融建议）强制触发合规检查；支持一轮内多跳工具调用（检索→计算→审查）并回写 Memory」 |
| 监控与反馈 | 调用日志、自检、指标如何回流优化 | 「采集工具调用次数/耗时/成功率指标，接入 Trace 回溯与 Reflection 自检，指标驱动 A/B 迭代」 |

叙事要点：面试官想看的不是「用了 ReAct」，而是「模型在什么情况下调用哪个工具、怎么调用、怎么保证合规与可控」。

## 4. 场景 → 架构 → 关键决策 改写框架

反面（功能描述，一眼假）：

> 开发智能客服 Agent，接入产品文档和订单系统，实现自动回复和退换货处理。

正面（问题解决，可追问）：

> 用户提问混杂闲聊与多轮意图跳转，单一意图识别准确率不足 70%。采用 ReAct 范式设计 Agent 主循环，把意图识别拆成门控路由 + 工具调用两步，降低单步 Prompt 推理负担。在 200 条真实客服对话测试集上，任务完成率从 58% 提升至 79%，单次对话平均耗时下降约 40%。

改写三步：先给场景约束（问题有多难）→ 再给架构选择与理由（你的判断力）→ 最后给量化结果或定性结论（可核验）。

## 5. 五类可验证表达（JD 高频，逐类核对）

### 5.1 Agent 应用项目 —— 业务场景 + 用户量 + 自动化率

- 反面：「负责公司 Agent 应用开发，使用 Coze 平台搭建客服机器人，对接微信公众号。」（无规模、无结果）
- 正面：「搭建电商客服 Agent，覆盖 200+ SKU 售前咨询场景，承接日均 5000+ 次用户咨询，自动应答率 78%，人工介入率从 65% 降至 22%，单次响应延迟 1.2s。」
- 指标模板：业务场景（一句话）→ 规模指标（用户量 / SKU / 调用量）→ 效果指标（自动化率、人工替代率）→ 性能指标（延迟、并发、稳定性）

### 5.2 工具调用项目 —— 工具数量 + 成功率 + 异常处理

- 反面：「实现 LLM 工具调用能力，支持多种外部 API 调用。」（几种？成功率？异常呢？）
- 正面：「集成 12 个外部工具（CRM、订单、物流、邮件等），工具调用成功率 94%，平均调用链长度 3.2 步；针对超时、参数错误、权限不足建立重试与降级机制，异常场景任务完成率从 71% 提升至 89%。」
- 指标模板：工具规模 → 调用指标（成功率、调用链长度、Token 消耗）→ 异常处理（重试 / 降级 / 错误日志）→ 异常场景下的改进结果
- 进阶写法：把异常预判写进工具定义层（如摘要超 4096 字符自动分片顺序发送，并在 Prompt 中约定切分规则保持语义连贯）——这是「设计工具调用体系」与「调了几个 API」的分水岭。

### 5.3 多 Agent 协作项目 —— Agent 数量 + 分工协议 + 效率提升

- 反面：「研究多 Agent 协作技术，使用 LangGraph 框架搭建多 Agent 系统。」
- 正面：「设计 4 Agent 协作架构（研究 / 数据分析 / 报告撰写 / 质量审核），Supervisor 模式协调任务分配；建立 Agent 间 JSON Schema 通信协议与状态管理机制，任务调度成功率 96%，日均自动产出 800+ 份报告，单报告耗时从人工 4 小时降至 12 分钟。」
- 指标模板：Agent 数量与角色分工 + 协作模式（Supervisor / Hierarchical / Collaborative）→ 通信协议与状态管理 → 任务量 / 产出量 → 相对人工的效率提升

### 5.4 知识库 / RAG 项目 —— 文档规模 + 检索准确率 + 采纳率

- 反面：「搭建企业知识库 Agent，支持文档问答功能。」
- 正面：「构建企业知识库 RAG 系统，覆盖产品手册、技术文档、FAQ 共 2.3 万份文档，BGE-large 向量化 + Milvus 存储，Top-5 检索准确率 92%，用户答案采纳率 85%；建立每日增量同步机制与 500 条人工标注种子的冷启动方案。」
- 指标模板：文档规模 → 技术栈（Embedding、向量库、检索策略）→ 效果指标（Top-K 准确率、采纳率、NDCG@10）→ 工程化（更新机制、冷启动、缓存与分块）

### 5.5 效果评估项目 —— 评估体系 + 对比实验 + 持续迭代

- 反面：「持续优化 Prompt，提升 Agent 回答质量。」（空话）
- 正面：「建立离线 + 在线评估体系：1000 条业务问题评估集 + 自动指标（LLM-as-Judge），在线 5% 流量 A/B 对照；3 个月内业务问题解决率从 72% 提升至 86%，人工兜底率从 28% 降至 14%。」
- 指标模板：评估集规模与构造方式 → 评估方法（离线指标 / LLM-as-Judge / A/B）→ 迭代机制（版本管理、回滚、对比）→ 业务结果

## 6. 写法禁忌（出现即改）

| 禁忌 | 为什么 | 怎么改 |
|---|---|---|
| 技术名词罗列（「熟练掌握 LangChain、Coze、RAG……」） | 无业务场景与结果，HR 初筛直接淘汰 | 名词进项目描述当证据，结果用数字收尾 |
| 「明显提升」「得到团队认可」 | 不可验证，等于没写 | 换成对比数字或测试集结论 |
| 「全链路架构师」式角色 | 面试一问就穿帮 | 写清你负责的那一层 |
| 把 Demo / 课程项目说成生产 | Agent 岗面试官多为框架深度用户，术语和细节一眼辨真假 | 如实标注项目性质，用测试集与评测量化 |
| 只写「调 API」「上线了」 | 是普通后端经历，不是 Agent 工程经历 | 补 Schema 设计、失败兜底、评测回归 |
| 技能栏堆 15 个关键词 | 无优先级 = 无信号 | 留 6-8 个与 JD 逐字一致的，其余入项目 |
| 应用项目堆模型内部术语（改 Attention Mask 等） | 投错面试官池 | 应用岗讲使用层：Prompt、检索、外层控制 |
| 量化提速降本不提质量 | 熟练面试官默认你在降质换速 | 写「质量不退化」前提与评测口径 |
